# Localization (l10n) — Proof of Concept Plan

This document is a hands-on, end-to-end plan for adding localization to the
Proton VPN GTK app using **GNU gettext** (Solution 1), implemented as a
**proof of concept on the login page**. It is written so you can follow it
without prior i18n experience and end up with a working French build you can
run and see.

> **Scope of the PoC:** translate everything the user sees on the login screen
> (username/password form, sign-in button, links, the kill-switch banner shown
> on the login page, and the two-factor-authentication forms). Wire up the
> tooling so that extending to the rest of the app later is just "mark more
> strings and re-run two commands".

---

## 0. Mental model in one paragraph

We mark every user-facing English string with a function call, conventionally
`_("...")`. A tool (**Babel**) scans the code, collects all marked strings into
a template file (`.pot`), and from that we create one editable text file per
language (`fr.po`). A human fills in the French. Babel compiles `fr.po` into a
binary `.mo` file that ships inside the Python package. At runtime, `_()` looks
the string up in the loaded `.mo` and returns the translation (or the original
English if there is none). gettext is in the Python standard library, so the
**app gains no new runtime dependency**; Babel is a **dev/build-time tool only**.

## 1. Before you write any code — checklist

Verify each of these first. They are the things that silently waste an
afternoon if skipped.

1. **The app builds and runs today.** Confirm you can launch it:
   `python -m proton.vpn.app.gtk` (or the installed `protonvpn-app`). You need a
   known-good baseline to compare against.
2. **Babel is available in your dev environment.** It is the extraction/compile
   tool. Add it to the `development` extra in `setup.py` (see §9) and
   `pip install -e ".[development]"`. Confirm `pybabel --version` works. Babel
   is pure-Python; it does **not** require the system `gettext` C tools.
3. **You can force a language without touching your OS.** Our runtime loads a
   specific `.mo` by name (see §6), so you do **not** need to generate system
   locales just to test translations. (You only need a generated system locale —
   e.g. `locale-gen fr_FR.UTF-8` — if you later want locale-aware number/date
   formatting via `locale.setlocale`.)
4. **Decide the product question now (it changes the design):**
   _Should the in-app language follow the OS, or be a separate setting the user
   picks inside the app?_ See §7. The PoC supports **both**, defaulting to the
   OS locale but allowing an override. Confirm with your team which is the real
   requirement.
5. **Know what must NOT be translated.** Do not mark:
   - **Log messages** — `logger.info(...)`, `logger.warning(...)` strings stay
     English (they are for engineers, and translating them breaks log parsing).
   - **URLs** — `https://account.protonvpn.com/...`, `https://protonvpn.com/support`.
   - **CSS class names / widget names** — `add_css_class("primary")`,
     `set_name("login-form")`.
   - **Example/placeholder codes that are not words** — `"123456"` and
     `"y5d6132f"` in the 2FA form are illustrative values; leave them. (Word
     placeholders like `"Username"` / `"Password"` _are_ translated.)
6. **Note the test impact up front.** Several unit tests assert against these
   string constants, e.g. `tests/unit/widgets/login/test_login_form.py:234`:
   `assert widget.get_label() == login_form.LOGGING_IN_MESSAGE`. Our design
   keeps these tests passing (see §8) — read that section before you start so
   you implement the lazy-string `__eq__` correctly.
7. **Mind the linters.** The repo enforces `flake8 max-line-length = 100`
   (`setup.cfg`). Wrapping strings in `_()` adds characters; some lines will
   need reflowing. CI runs `flake8`, `pylint`, and `mypy`.
8. **Python target is `>=3.9`.** Everything here is stdlib-compatible with 3.9.

**Why two locations for catalogs?**
`po/` holds the _human-editable_ sources (`.pot`, `.po`) — these are what
translators touch and what goes to a platform like Crowdin/Weblate later.
`proton/vpn/app/gtk/locale/` holds the _compiled_ `.mo` files that the running
app reads; they live inside the package so they are shipped exactly like the
existing `assets/` directory.

**Text domain** = `proton-vpn-app`. This is the namespace that keeps our catalog
separate from GTK's own. The compiled file is always named
`<domain>.mo` and lives at `<locale_dir>/<lang>/LC_MESSAGES/<domain>.mo`.

## 3. The translator module — `proton/vpn/app/gtk/translator.py` (new)

This is the heart of the PoC. It exposes the markers used throughout the code.

```python
"""
Localization helpers for the Proton VPN GTK app.

Usage:
    from proton.vpn.app.gtk.translator import _, N_, L_

    label = Gtk.Label(label=_("Sign in"))          # inline strings
    MY_CONSTANT = L_("Signing in...")               # class-body constants (lazy)

Copyright (c) 2023 Proton AG  --  GPLv3 (keep the standard header here)
"""
import gettext
import os

#: gettext "text domain": the catalog namespace and the .mo filename stem.
DOMAIN = "proton-vpn-app"

#: Directory that contains <lang>/LC_MESSAGES/<DOMAIN>.mo
LOCALE_DIR = os.path.join(os.path.dirname(__file__), "locale")

# The currently active catalog. `fallback=True` => if no .mo matches, _()
# returns the original English string instead of raising. With no `languages`
# argument, gettext picks the language from the environment (LANGUAGE/LC_ALL/
# LC_MESSAGES/LANG) — i.e. it follows the OS by default.
_translation = gettext.translation(DOMAIN, LOCALE_DIR, fallback=True)


def _(message: str) -> str:
    """Translate `message` using the active catalog (runtime lookup)."""
    return _translation.gettext(message)


def ngettext(singular: str, plural: str, n: int) -> str:
    """Plural-aware translation (handles language-specific plural rules)."""
    return _translation.ngettext(singular, plural, n)


def N_(message: str) -> str:
    """No-op marker: makes a string extractable without translating it now.

    Use when the string must remain a plain `str` at definition time but you
    still want the extractor to see it. The actual translation is applied later
    by passing it through `_()`.
    """
    return message


class _LazyString:
    """A string proxy that is translated *when rendered*, not when created.

    This solves the class-constant problem: class bodies execute once, at import
    time — before the language is necessarily chosen. A `_LazyString` defers the
    `_()` lookup until it is turned into text (`str()`), so it always reflects
    the language that is active at render time, and a runtime language change is
    picked up automatically.
    """
    __slots__ = ("_msgid",)

    def __init__(self, msgid: str):
        self._msgid = msgid

    def __str__(self) -> str:
        return _(self._msgid)

    # Make `_LazyString` behave like the translated text in comparisons and
    # formatting. This keeps existing unit tests working, e.g.
    #   assert widget.get_label() == SomeWidget.SOME_CONSTANT
    # where get_label() returns a plain translated `str`.
    def __eq__(self, other) -> bool:
        return str(self) == other

    def __hash__(self) -> int:
        return hash(str(self))

    def __repr__(self) -> str:
        return f"_LazyString({self._msgid!r})"


def L_(message: str) -> "_LazyString":
    """Lazy translation marker for module/class-level constants."""
    return _LazyString(message)


def set_language(language_code: str | None) -> None:
    """Switch the active catalog at runtime.

    :param language_code: e.g. "fr", "de". Pass None to follow the OS locale.
    """
    global _translation  # noqa: PLW0603 — intentional module-level rebinding
    languages = [language_code] if language_code else None
    _translation = gettext.translation(
        DOMAIN, LOCALE_DIR, languages=languages, fallback=True
    )
```

Key points to understand:

- `_()` does the **runtime** lookup. `L_()` wraps a string so the lookup is
  **deferred** until the widget renders it — required for the `CONSTANT = "..."`
  pattern this codebase uses heavily.
- `N_()` only _marks_ a string for extraction and returns it unchanged; you use
  it for the rare case where a real `str` is needed at definition time.
- `set_language()` is what makes the app language **independent of the OS** (§7).
- `_LazyString.__eq__/__hash__` exist specifically so the current tests keep
  passing (§8).

## 4. Bind the text domain at startup — `proton/vpn/app/gtk/__init__.py` (edit)

This file already runs first (it configures logging) and is imported before any
widget module. That makes it the correct place to initialize locale handling,
**before** widget classes — and their `L_()` constants — are defined.

Add, after the existing imports:

```python
import locale  # add near the top with the other stdlib imports

from proton.vpn.app.gtk.translator import DOMAIN, LOCALE_DIR  # noqa: E402

# Adopt the user's environment locale for number/date formatting, etc.
# Guarded because a misconfigured machine can lack the requested locale.
try:
    locale.setlocale(locale.LC_ALL, "")
except locale.Error:
    pass

# Bind the C-side gettext domain so that strings rendered by GTK/GLib helpers
# (and our own catalog) resolve from our locale directory.
try:
    locale.bindtextdomain(DOMAIN, LOCALE_DIR)
    locale.textdomain(DOMAIN)
except AttributeError:
    # locale.bindtextdomain is not available on every platform; the Python-side
    # gettext in translator.py still works without it.
    pass
```

> The Python-side lookups in `translator.py` work on their own. The
> `locale.bindtextdomain` calls additionally cover any text produced by the C
> side of GTK using the same domain. Keep both for correctness.

## 6. How the language is chosen at runtime (and why it's decoupled from the OS)

`gettext.translation(DOMAIN, LOCALE_DIR, languages=[...])` reads exactly the
`.mo` you name. Because `translator.set_language("fr")` passes an explicit
language list, **the displayed language is fully under the app's control and
need not match the operating system**. With no language list, gettext falls
back to the environment (`LANGUAGE`/`LC_ALL`/`LC_MESSAGES`/`LANG`) — i.e. it
follows the OS. The PoC supports both; see §7 for wiring a setting.

---

## 7. OS-follow vs. in-app language setting

- **Follow the OS (zero UI):** do nothing extra. On startup the default
  `_translation` already uses the environment. Test with
  `LANGUAGE=fr protonvpn-app`.
- **In-app override (recommended end state):**
  1. Persist a `language` preference (e.g. `"fr"`, or `"system"` to follow OS)
     in the app settings object provided by `proton-vpn-api-core`, alongside
     existing prefs like kill switch / DNS.
  2. At startup, after `__init__.py` runs, read the saved value and call
     `translator.set_language(saved_value or None)` **before** the main window
     is built.
  3. Add a "Language" dropdown in the settings window
     (`widgets/headerbar/menu/settings/`) that, on change, saves the pref and
     calls `set_language(...)`.

> **Live switching caveat:** because constants use `L_()` (lazy), newly drawn
> widgets pick up the new language immediately, but widgets already on screen
> that cached a resolved `str` will not refresh until rebuilt. For the PoC,
> applying the language on next launch is simplest; full live switching is a
> later iteration. This is the main product decision flagged in §1.4.

## 8. Test impact — keep CI green

Some unit tests compare a widget's rendered label to the constant, e.g.
`tests/unit/widgets/login/test_login_form.py`:

```python
assert widget.get_label() == login_form.LOGGING_IN_MESSAGE
```

`get_label()` returns a plain translated `str`; `LOGGING_IN_MESSAGE` is now a
`_LazyString`. The `__eq__`/`__hash__` we added in §3 make
`str == _LazyString` and `_LazyString == str` both work, so **these assertions
keep passing** as long as the active catalog is the (English) fallback during
tests — which it is, since no `fr.mo` is loaded in the unit-test environment and
`_()` then returns the original English.

Tests like
`notifications_mock.show_error_message.assert_called_once_with(LoginForm.INVALID_USERNAME_MESSAGE)`
also pass: the code passes the same `_LazyString` object the assertion
references, so they compare equal by identity/`__eq__`.

**Action items:**

- Run `pytest tests/unit/widgets/login` after the edits — expect green.
- If any test imported a constant and did string operations on it (slicing,
  `.format`), wrap with `str(...)` in the test, or add the needed dunder to
  `_LazyString`.
- Add one new test asserting translation works (see §12).

## 10. Extraction config & commands

### `babel.cfg` (new) — tells pybabel to treat the tree as Python

```ini
[python: proton/vpn/app/gtk/**.py]
```

### `po/POTFILES.in` (new, optional)

A human-readable list of the files that contain strings. Not strictly required
when using the glob in `babel.cfg`, but useful documentation:

```
proton/vpn/app/gtk/widgets/login/login_form.py
proton/vpn/app/gtk/widgets/login/disable_killswitch.py
proton/vpn/app/gtk/widgets/login/two_factor_auth/two_factor_auth_widget.py
proton/vpn/app/gtk/widgets/login/two_factor_auth/authenticator_app_form.py
proton/vpn/app/gtk/widgets/login/two_factor_auth/security_key_form.py
```

### Commands (run from the repo root)

**1. Extract** all marked strings into the template. The `-k` flags register our
custom markers so Babel recognizes `N_`, `L_`, and `ngettext`:

```bash
pybabel extract -F babel.cfg \
  -k _ -k N_ -k L_ -k ngettext:1,2 \
  -o po/proton-vpn-app.pot \
  --project="Proton VPN" \
  proton/
```

**2. Create the French catalog** (first time only):

```bash
pybabel init -i po/proton-vpn-app.pot -d po -D proton-vpn-app -l fr
# creates po/fr/LC_MESSAGES/proton-vpn-app.po
```

> Tip: many teams keep the working `.po` directly at `po/fr.po`. If you prefer
> that flat layout, run `pybabel init` then move/symlink, or pass the explicit
> output path. Keep it consistent with whatever your translation platform
> expects.

**3. (Later) Update** existing catalogs after strings change — this preserves
already-translated entries and flags changed ones as "fuzzy":

```bash
pybabel update -i po/proton-vpn-app.pot -d po -D proton-vpn-app
```

**4. Compile** `.po` → `.mo` into the **shipped** locale dir:

```bash
pybabel compile -d proton/vpn/app/gtk/locale -D proton-vpn-app \
  --use-fuzzy
# produces proton/vpn/app/gtk/locale/fr/LC_MESSAGES/proton-vpn-app.mo
```

> Note the **two different `-d` directories on purpose**: extraction/update work
> in `po/` (sources), compile writes into the package `locale/` (runtime). Set
> up your compile step to read `po/` and write `locale/`; if `pybabel compile`
> requires the same layout, copy `po/<lang>/LC_MESSAGES/*.po` into
> `proton/vpn/app/gtk/locale/<lang>/LC_MESSAGES/` before compiling, or compile
> in place and copy the `.mo`. The Makefile in §11 encapsulates this.

## 11. `Makefile` (new, optional but recommended)

```make
DOMAIN = proton-vpn-app
POTFILE = po/$(DOMAIN).pot
LOCALEDIR = proton/vpn/app/gtk/locale

.PHONY: i18n-extract i18n-update i18n-compile

i18n-extract:
	pybabel extract -F babel.cfg -k _ -k N_ -k L_ -k ngettext:1,2 \
		-o $(POTFILE) --project="Proton VPN" proton/

i18n-update: i18n-extract
	pybabel update -i $(POTFILE) -d po -D $(DOMAIN)

i18n-compile:
	pybabel compile -d po -D $(DOMAIN) --use-fuzzy
	# copy compiled catalogs into the shipped package tree
	@for po in po/*/LC_MESSAGES/$(DOMAIN).po; do \
		lang=$$(echo $$po | cut -d/ -f2); \
		mkdir -p $(LOCALEDIR)/$$lang/LC_MESSAGES; \
		msgfmt $$po -o $(LOCALEDIR)/$$lang/LC_MESSAGES/$(DOMAIN).mo 2>/dev/null \
			|| cp po/$$lang/LC_MESSAGES/$(DOMAIN).mo $(LOCALEDIR)/$$lang/LC_MESSAGES/; \
	done
```

## 12. Producing the French translation (`po/fr.po`)

After extraction the `.pot` contains entries like:

```po
#: proton/vpn/app/gtk/widgets/login/login_form.py:78
msgid "Sign in"
msgstr ""
```

A human (you, for the PoC) fills in `msgstr`. A representative `po/fr.po` for the
login page:

```po
msgid ""
msgstr ""
"Project-Id-Version: Proton VPN\n"
"Content-Type: text/plain; charset=UTF-8\n"
"Content-Transfer-Encoding: 8bit\n"
"Language: fr\n"
"Plural-Forms: nplurals=2; plural=(n > 1);\n"

#: proton/vpn/app/gtk/widgets/login/login_form.py:70
msgid "Username"
msgstr "Nom d'utilisateur"

#: proton/vpn/app/gtk/widgets/login/login_form.py:75
msgid "Password"
msgstr "Mot de passe"

#: proton/vpn/app/gtk/widgets/login/login_form.py:78
msgid "Sign in"
msgstr "Se connecter"

msgid "Signing in..."
msgstr "Connexion en cours..."

msgid "Invalid username."
msgstr "Nom d'utilisateur invalide."

msgid "Incorrect credentials."
msgstr "Identifiants incorrects."
```

## 14. Gotchas, recap

- **Do not wrap log messages, URLs, CSS class names, or non-word example codes.**
- **Class-body constants must use `L_()` (lazy), not `_()`** — otherwise the
  language is frozen at import time.
- **Identical strings merge** in the catalog automatically.
- **Keep lines ≤ 100 chars** for flake8 after wrapping.
- **`.po` is edited by humans; `.mo` is generated** — never hand-edit `.mo`, and
  regenerate `.mo` whenever `.po` changes.
- **Babel does not translate** — it extracts, merges, and compiles. Humans (or a
  platform like Crowdin/Weblate) provide the actual `msgstr` text.
- **Country/city names** shown elsewhere come from `proton-vpn-api-core`, not
  this repo; they are out of scope here and localized upstream.
- **The `.desktop` file** (`rpmbuild/SOURCES/proton.vpn.app.gtk.desktop`) is
  localized separately via `Name[fr]=` / `Comment[fr]=` keys — not part of the
  login PoC, but note it for full coverage.
